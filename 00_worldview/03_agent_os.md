# Agent OS：从操作系统到智能体运行时

Agent OS 可以作为这套笔记进入 AI 时代后的新主题。

这里的 Agent OS 不是说马上要做一个真正的操作系统，而是用操作系统的视角理解 Agent 运行时：当 LLM 不再只是聊天模型，而是能读文件、改代码、跑命令、调用外部服务、拆任务、恢复会话时，它需要一套类似操作系统的工程基础设施。

## Agent = LLM + Harness

LLM 本身可以理解成一个函数：

```text
next_token = f(context)
```

它根据上下文预测输出。这个函数很强，但它自身不能直接访问文件系统、不能真实运行命令、不能知道当前仓库怎么测试、不能保证自己遵守项目规则，也不能天然保存长期任务状态。

所以需要 Harness。

```text
Agent = LLM + Harness
```

Harness 是模型之外的一切工程基础设施：

- 指令：system prompt、`CLAUDE.md`、`AGENTS.md`、Commands、Skills。
- 上下文：文件、对话历史、检索结果、任务计划、压缩摘要。
- 工具：shell、文件读写、git、浏览器、MCP、数据库、GitHub。
- 环境：依赖、运行时、项目结构、测试命令、权限边界。
- 状态：会话、checkpoint、任务列表、进度文件、仓库历史。
- 反馈：测试、lint、构建、日志、用户确认、review。

模型决定“下一步想做什么”，Harness 决定“它能看到什么、能做什么、怎么验证、如何恢复”。

## 和操作系统的对应关系

这个类比不是为了把概念说得玄，而是为了借用操作系统里已经成熟的问题框架。

| 操作系统 | Agent OS |
|---|---|
| 进程 | Agent 会话、Subagent、任务执行上下文 |
| 内存 | Context window、短期上下文、压缩摘要 |
| 文件系统 | 仓库、文档、进度文件、会话记录 |
| 系统调用 | Tool call |
| 设备驱动 | MCP Server、插件、外部 API 适配器 |
| shell | Claude Code / Codex CLI / 图形化 Agent 控制台 |
| 权限模型 | 工具白名单、确认机制、沙箱、Hook 拦截 |
| 中断 | 用户打断、Hook、测试失败、工具错误 |
| 调度 | 主 Agent 分配任务、Subagent 并行、队列与优先级 |
| 日志 | tool log、conversation export、CI 日志 |
| 快照和回滚 | checkpoint、rewind、git commit/worktree |
| 配置文件 | `CLAUDE.md`、`AGENTS.md`、settings、commands、skills |

这里最关键的对应是：

```text
Tool call 对 Agent，就像 syscall 对应用程序。
```

应用程序自己不能直接操作所有硬件，它通过系统调用请求内核。LLM 自己也不能直接改变外部世界，它通过工具调用请求 Harness。

## Claude Code 是一个低层 Agent Harness

Claude Code 的特点是 low-level、unopinionated。它不像一个封闭的“AI 应用”，而更像一个给程序员使用的 Agent 运行时。

它提供了几类基础能力：

- CLI 入口：可以交互，也可以 `claude -p` 放进 Unix 管道。
- 项目上下文：通过 `CLAUDE.md`、文件读取、搜索理解仓库。
- 工具调用：读写文件、执行 shell、使用 git、调用 MCP。
- 权限系统：工具调用需要确认，也可以配置允许范围。
- 会话管理：继续会话、压缩上下文、导出对话、checkpoint。
- 扩展机制：Commands、Skills、Hooks、Subagents。

从你的系统视角看，Claude Code 的价值不是“帮我写代码”这么窄，而是提供了一个可以实验 Agent OS 的低层平台。

## Commands 和 Skills 是自然语言程序

你已经写到一个很重要的判断：

> Command / Skill ~= 面向 AI Agent 的自然语言程序。

这可以继续深化。

传统程序大致是：

```text
源代码 + 编译器/解释器 + 运行时 + 输入 -> 输出
```

Agent Command / Skill 大致是：

```text
自然语言说明 + LLM Agent + Harness + 工具权限 + 输入 -> 输出
```

它不是传统意义上的确定性程序，但也不是随便一段 prompt。一个好的 Command/Skill 至少包含：

- 名字和调用方式；
- 参数约定；
- 可用工具；
- 执行步骤；
- 判断规则；
- 输出格式；
- 验收标准；
- 示例和参考材料。

所以 Skill 更像一个“小应用包”：

```text
SKILL.md + references + scripts + examples + tests
```

它的运行时不是 Python/Node，而是 Agent。

## Hooks 是软规则变硬约束

单纯写在 prompt 里的规则，Agent 可能会忘。Hook 的价值是把规则放进运行时：

- UserPromptSubmit：用户输入后、模型处理前补充上下文或策略。
- PreToolUse：工具执行前检查权限和危险行为。
- PostToolUse：工具执行后格式化、测试、记录日志。

这和操作系统/嵌入式里的很多机制相似：

- 中断：事件发生后强制执行一段处理逻辑。
- 权限检查：访问资源前先判断是否允许。
- Watchdog：系统异常时触发恢复机制。
- CI hook：代码变化后自动验证。

Hooks 的本质不是让模型更聪明，而是让工作流更稳定。

## MCP 是 Agent 的外设总线

MCP 的意义是把外部能力标准化。

没有 MCP 时，每个 AI 产品都要单独适配 GitHub、数据库、浏览器、搜索、文件系统。MCP 把这些能力统一成 Server，暴露 tools、resources、prompts。

这很像设备驱动模型：

- 外部服务本身像设备。
- MCP Server 像驱动或适配层。
- MCP Client 像内核里的统一接入框架。
- Tool schema 像设备能力描述。

也很像网络协议：

- 双方按 JSON-RPC 说话。
- 本地可以走 stdio。
- 远程可以走 HTTP。
- 能力发现和调用过程标准化。

所以 MCP 可以放到“系统如何连接”这一卷，而不是只放在“Claude Code 用法”里。

## Subagent 是并发和分工问题

Subagent 不只是“多开几个 AI”。它真正触及的是任务调度和上下文隔离。

适合 Subagent 的任务有明显特征：

- 边界清晰；
- 可以独立阅读上下文；
- 不需要频繁与用户交互；
- 输出可以被主 Agent 汇总；
- 最好不要同时改同一批文件。

这和操作系统里的进程/线程有相似问题：

- 什么时候并发能提高效率？
- 共享状态如何控制？
- 子任务失败如何回收？
- 主任务如何整合结果？
- 多个执行者如何避免互相覆盖？

Agent Team 则更接近组织层面的调度：Team Lead、Reviewer、Implementer、Critic、Researcher。这已经不只是工具使用，而是软件工程流程被 Agent 化。

## 仓库是 Agent 的系统记录

Harness Engineering 里最重要的一条是：

```text
Agent 看不到的东西，对它来说就不存在。
```

这和操作系统文件系统的角色类似。文件系统不只是存文件，而是系统状态的持久化表达。对 Agent 来说，仓库也不只是代码目录，而是项目事实来源。

因此仓库里应该能回答五个冷启动问题：

1. 这是什么系统？
2. 项目怎么组织？
3. 怎么运行？
4. 怎么验证？
5. 现在做到哪了？

如果这些答案只存在于人的脑子里，Agent 就只能猜。猜错后再修，比一开始把信息显式化成本更高。

这和你过去写嵌入式时的经验一致：芯片手册、链接脚本、设备树、Makefile、rootfs、驱动注册信息，都是系统能否被另一个人接手和理解的事实来源。

## Agent OS 要解决的六个问题

结合前面的“五个问题”，Agent OS 可以定义为解决以下问题的运行时：

### 1. 意图表达

人如何用自然语言、命令、设计文档、issue、任务列表表达目标。

### 2. 上下文管理

哪些文件、规则、历史、计划、错误日志应该进入上下文。什么时候压缩，什么时候清空，什么时候恢复。

### 3. 工具中介

模型如何发现工具，如何选择工具，如何传参，如何处理工具失败。

### 4. 权限和资源

哪些文件能读写，哪些命令能执行，哪些操作需要确认，token 和时间如何控制。

### 5. 反馈闭环

如何通过测试、构建、lint、运行结果、用户 review、CI 日志，让 Agent 知道自己是否做对。

### 6. 状态持久化

长任务如何跨会话继续，项目决策如何沉淀，进度如何记录，失败后如何回滚。

如果这六个问题没有被设计好，Agent 会显得“有时很强，有时很不靠谱”。但问题往往不只是模型，而是 Harness 断了。

## 和传统操作系统不同的地方

这个类比也有边界。

传统程序大多是确定性执行；Agent 是概率模型驱动的受约束推理流程。

传统系统调用参数由程序显式计算；Agent 的工具参数可能来自自然语言理解和上下文推断。

传统操作系统更关注 CPU、内存、设备；Agent OS 更关注上下文、工具、权限、反馈和任务状态。

传统 bug 大多可复现；Agent 错误有时来自上下文缺失、任务歧义、模型不确定性或反馈不足。

所以 Agent OS 不是把操作系统概念机械搬过来，而是借用它的问题意识：

```text
当一个执行主体要长期、可靠、安全地操作复杂环境时，运行时必须管理边界、状态、资源和反馈。
```

## 后续研究方向

可以把 Claude Code 研究分成三层：

### 使用层

- 基础命令、会话、上下文、权限。
- `CLAUDE.md` 怎么写。
- Commands、Skills、Hooks、Subagents 怎么用。
- 和 git、测试、CI、文档协作。

### 原理层

- LLM 如何基于 context 输出下一步。
- 工具调用如何被 Harness 执行。
- MCP 如何完成能力发现和调用。
- Hooks 如何在工具调用前后插入确定性逻辑。
- 子代理如何隔离上下文并汇总结果。

### 系统层

- 如何设计项目级 Harness。
- 如何做冷启动测试。
- 如何让仓库成为唯一事实来源。
- 如何构建反馈闭环。
- 如何把 Agent 工作流纳入团队工程流程。

最终目标不是写一份 Claude Code 使用手册，而是形成一套判断：

**AI 时代的软件工程，不只是会问模型，而是会设计让模型稳定工作的系统。**
