# 系统构造的五个问题

这个仓库里已经出现过一个很好的结构：系统构造的五个问题。

原来的版本是：

1. 计算是什么？
2. 控制如何建立？
3. 资源如何分配？
4. 系统如何连接？
5. 复杂性如何被管理？

这五个问题比“课程分类”更稳定。课程会变，工具会变，框架会变，但只要是在构造技术系统，就绕不开这些问题。

## 1. 计算是什么

计算不是从 C 语言开始的，也不是从 CPU 开始的。更底层的表达是：

```text
计算 = 状态 + 状态迁移规则
```

数字电路里，状态是寄存器，迁移规则是组合逻辑。CPU 里，状态是内存、寄存器和 PC，迁移规则是指令执行。C 程序里，状态是变量、堆、栈和控制流，迁移规则是语句执行。操作系统里，状态扩展成进程、文件、设备、内存映射和调度队列。

你在笔记里对这件事已经有很强的表达：

- 状态如何被存储？
- 指令如何改变状态？
- 程序如何驱动状态变化？
- 程序为什么可以被调试？
- 编译器如何把一个状态机翻译成另一个状态机？

所以“计算是什么”这一卷，不只是编程基础，而是对状态、表示、转换和可计算性的理解。

对应内容：

- C/C++：表达状态迁移规则的语言。
- 数据结构：状态的组织方式。
- 算法：状态迁移策略。
- CSAPP：从源代码到机器状态迁移。
- 数字电路和组成原理：计算的物理实现。
- SICP/PL：计算表达和抽象机制。

## 2. 控制如何建立

控制不是狭义的控制理论，而是一个系统中“谁能让什么发生变化”的问题。

在计算机系统里，控制首先表现为控制权转移：

- CPU reset 后，第一条指令在哪里？
- Firmware 如何把控制权交给 bootloader？
- bootloader 如何把控制权交给 kernel？
- kernel 如何启动 init？
- 应用程序如何通过 `syscall` 把控制权交给操作系统？
- 中断如何强行夺回控制权？
- shell 如何把人的命令翻译成进程、文件描述符和系统调用？

你把 The Missing Semester 里的 shell、git、make、调试工具放到“控制如何建立”下，其实很准确：

- shell 是流程控制。
- make 是构建控制。
- git 是历史和协作控制。
- gdb/strace 是对状态迁移的观察和干预。
- 测试是对系统行为的反馈控制。

在 Agent 系统里，同一个问题继续出现：

- 人如何把意图交给 Agent？
- Agent 如何决定调用哪个工具？
- 工具调用前是否需要权限确认？
- Hook 如何拦截危险行为？
- 测试失败后，Agent 如何修正行为？
- 会话中断后，任务状态如何恢复？

所以“控制如何建立”这一卷可以成为从 boot chain 到 Agent workflow 的连接点。

## 3. 资源如何分配

操作系统的核心是资源管理。你已经把它概括为：

```text
操作系统 = 对象 + API
```

操作系统把硬件资源变成对象，再提供 API 让程序使用：

- CPU 时间变成进程、线程、调度。
- 内存变成地址空间、页、映射。
- 磁盘变成文件和文件系统。
- 设备变成设备节点、驱动、文件描述符。
- 并发冲突变成锁、条件变量、信号量。

RTOS 是这条线的简化版：线程、调度、同步、设备框架。Linux 是这条线的成熟工业版：虚拟内存、进程隔离、驱动模型、文件系统、网络栈。

Agent 系统里同样要分配资源，只是资源类型变了：

- context window 是稀缺内存。
- tool call 是昂贵的外部能力。
- token 和费用是运行成本。
- 子代理是并发执行资源。
- 文件和仓库是持久状态。
- 用户注意力也是资源。

因此 Agent OS 也必须回答资源分配问题：哪些上下文该保留，哪些应该压缩；哪些工具可以调用，哪些需要确认；哪些任务适合拆给 subagent，哪些应该留在主会话。

## 4. 系统如何连接

单机系统足够复杂，但真正的工程系统一定会跨边界。

网络笔记里的问题是：

- 浏览器如何把一个 URL 变成网络请求？
- 数据包如何跨网卡、交换机、路由器、运营商和服务器？
- 协议如何在不可靠环境中建立可靠通信？
- 系统边界跨越机器时，如何仍然保持秩序？

嵌入式系统里也有同样的问题：

- MCU 和外设如何通过 GPIO/UART/SPI/IIC/CAN 连接？
- Linux 用户态和内核态如何通过 syscall、sysfs、ioctl、mmap 连接？
- A 核和 M 核如何通过 RPMsg/OpenAMP 连接？
- 驱动和设备如何通过 bus/device/driver 模型连接？

Agent 系统里，MCP 正好落在这个问题上。

MCP 的意义不是“多了一个插件协议”，而是给 Agent 和外部系统之间建立统一连接方式：

```text
Agent Client -> MCP Protocol -> MCP Server -> Tool / Resource / Prompt
```

这很像网络协议，也很像设备驱动模型。外部能力不再直接写死到某个产品里，而是通过标准协议暴露出来。

## 5. 复杂性如何被管理

复杂性不是错误，而是系统发展到一定规模后的自然结果。

你的笔记里对复杂性的处理方式大致有几种：

- 分层：电路、ISA、汇编、高级语言、库、操作系统、应用。
- 抽象：文件、进程、线程、设备、socket、对象、API。
- 模型：状态机、最小程序、玩具操作系统、模拟器。
- 工具：gdb、strace、qemu、make、git、menuconfig。
- 约束：权限、系统调用、驱动模型、编码规范、测试。
- 反馈：调试、日志、测试、CI、运行结果。

这说明你并不是在追求“把所有细节背下来”，而是在追求一种可复用的复杂性管理框架。

Agent 时代这件事更重要。LLM 可以很快生成大量内容，但如果没有结构，复杂性会增长得更快。Harness Engineering 本质上就是在管理 Agent 工作流的复杂性：

- 指令子系统管理意图。
- 上下文子系统管理知识。
- 工具子系统管理外部能力。
- 环境子系统管理可执行条件。
- 状态子系统管理长期任务。
- 反馈子系统管理正确性。

## 第六个问题：意图如何进入系统

AI Agent 让这套结构多出了一个新问题：

```text
人的意图如何进入系统？
```

传统软件里，意图通常经过这样的路径：

```text
人的想法 -> 源代码 -> 编译器 -> 机器码 -> 操作系统 -> 硬件 -> 现实效果
```

Agent 系统里，路径变成：

```text
人的想法 -> 自然语言任务 -> LLM -> Harness -> Tool / Code / Shell / Git -> 现实效果
```

这不是说代码会消失，而是说意图进入机器的接口正在上移。过去程序员写代码，现在程序员还要设计 Agent 能理解、能执行、能验证、能恢复的工作环境。

因此五个问题可以扩展为六个：

1. 计算是什么：状态如何表示与转换？
2. 意图如何进入系统：人如何表达目标？
3. 控制如何建立：谁在什么时候拥有控制权？
4. 资源如何分配：状态、算力、工具、权限如何管理？
5. 系统如何连接：边界如何跨越？
6. 复杂性如何被管理：系统如何在增长后仍可理解、可验证、可演进？

这可以作为后续整理 `embedded-system` 的稳定主干。
