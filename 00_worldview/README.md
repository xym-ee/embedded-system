# 00 Worldview：计算、控制与 Agent OS

这个目录不是新的课程目录，而是对现有笔记的抽象总结层。

过去几年的材料里，表面上有很多不同主题：C/C++、CSAPP、数字电路、操作系统、RTOS、Linux 驱动、网络、Claude Code、Harness Engineering。它们看起来像不同方向的学习记录，但背后其实反复出现同一组问题：

- 人的意图如何进入机器？
- 状态如何被表示、存储和改变？
- 控制权如何在不同层级之间转移？
- 资源如何被隔离、分配和调度？
- 系统边界跨出去以后，如何仍然保持秩序？
- 复杂性增长以后，靠什么继续理解和控制系统？

如果用一句话概括这套笔记的主线：

**技术系统是在约束条件下，把人的意图翻译成可执行的状态迁移，并通过反馈让它稳定作用于现实世界。**

## 五年里的主线变化

2021 年的起点，是把计算机理解成一种强大的工程工具。重点还在“为什么工科学生需要掌握计算机基础”：控制、机器人、传感器、嵌入式系统都离不开计算平台。

2022 年开始，`hello world` 变成了一条贯穿软硬件的线索：源代码、编译、链接、加载、内存、寄存器、系统调用、显示设备。这里已经不只是“学一门课”，而是在追问一个程序从人的文本变成机器行为的全过程。

2023 年的嵌入式理解，开始从 MCU 裸机走向 RTOS 和 Linux。你反复写到：裸机能让人把握细节，但规模一大，就必须引入调度、对象、驱动、文件系统、构建系统、编码思想。这是从“能控制硬件”走向“能管理复杂性”。

2024 年回头看 RT-Thread 和 Linux 驱动时，一个更深的想法出现了：大的系统和小的系统在原理上相通。先完全理解一个小而完整的系统，再去理解 Linux 这类真实复杂系统，这比一开始硬啃庞大源码更稳。

2025 到 2026 年，LLM、Claude Code、Codex、MCP、Skills、Hooks、Subagent、Harness Engineering 出现以后，原来的问题并没有消失，而是换了形式：

- prompt 像不像新的程序语言？
- Agent 是不是新的执行环境？
- Tool/MCP 像不像系统调用和驱动接口？
- Hooks、权限和测试是不是新的控制与反馈机制？
- 仓库作为唯一事实来源，是不是新的文件系统和系统记录？

所以 AI Agent 不是这套笔记的外来分支。它是原来“计算机系统如何被构造和管理”这条线在 AI 时代的延伸。

## 核心判断

### 1. 状态机是底层共同语言

你在操作系统笔记里反复强调“程序是状态机”“计算机是状态机”“操作系统是状态机的管理者”。这个观点可以继续扩展：

- 数字电路：寄存器和组合逻辑决定下一状态。
- CPU：内存、寄存器和 PC 构成机器状态。
- C 程序：堆、栈、全局变量和控制流构成语言层状态。
- 操作系统：进程、文件、设备、内存映射构成被管理的状态集合。
- 网络系统：多个状态机通过消息和协议交换状态。
- Agent 系统：上下文、工具结果、文件、任务列表、测试反馈构成可演进的工作状态。

这说明“状态机”不是某门课里的概念，而是你理解系统的统一坐标系。

### 2. 抽象不是把细节藏起来，而是建立可控接口

ISA 把电路抽象成指令，操作系统把硬件抽象成对象和 API，RTOS 把裸机循环抽象成线程和调度，Linux 设备模型把硬件抽象成 device、driver、bus。

现在 Agent 也在做类似的事：

- Prompt 把人的意图抽象成任务说明。
- Tool 把外部能力抽象成可调用函数。
- MCP 把工具接入抽象成统一协议。
- Skill/Command 把经验流程抽象成可复用的自然语言程序。
- Harness 把模型之外的环境、工具、状态、反馈抽象成运行时。

抽象真正有价值的地方，不是让人“不知道下面发生了什么”，而是让人在合适的层级上控制系统。

### 3. 操作系统是理解 Agent OS 的原型

你对操作系统的定义很有自己的味道：

> 操作系统 = 对象 + API。

从应用视角看，操作系统就是 `syscall`；从硬件视角看，操作系统就是一个拥有完整控制权的程序；从数学视角看，操作系统是状态机的管理者。

把这个视角迁移到 Agent：

- Agent 看到的外部世界，是一组工具调用。
- Tool call 类似系统调用，越过模型自身能力边界。
- Harness 类似运行时和操作系统，负责权限、环境、状态和反馈。
- Agent OS 要管理的不只是 CPU 和内存，而是上下文、工具、任务、文件、外部服务和人的意图。

这不是简单类比，而是同一类问题的上移：当执行主体从传统程序变成 LLM Agent，系统仍然需要边界、权限、资源、调度和反馈。

### 4. 工具链和环境不是外围，它们是系统本体

你写过很多工具：gcc、gdb、strace、make、shell、qemu、交叉编译、NFS、TFTP、menuconfig、设备树、CLAUDE.md、MCP、Hooks。它们不是“辅助材料”，而是系统能否被理解、构建和验证的关键部分。

这也是 Harness Engineering 的核心：

**模型失败，很多时候不是模型本身不行，而是环境、上下文、验证、状态管理没有被设计好。**

换成你原来的语言就是：一个控制系统不稳定，不一定是控制算法不先进，也可能是传感器、执行器、采样、时延、电源、机械结构或调试工具出了问题。

### 5. 最小可运行系统是你的学习方法

你的笔记里反复出现同一个方法：

- 用 `hello world` 看完整计算机系统。
- 用 `minimal.S` 看程序和 syscall。
- 用 512 Byte MBR 看启动链。
- 用玩具操作系统看进程、调度和系统调用。
- 用 RT-Thread 看 Linux 驱动模型的简化版。
- 用 STM32/gcc 裸机开发看芯片启动和工具链。
- 用小项目实验 Claude Code，而不是先追所有概念。

这可以明确总结成一句方法论：

**先 100% 理解一个小而完整、原理相通的系统，再把它映射到真实复杂系统。**

这条方法也适用于 Agent OS。不要一开始就追所有平台和所有插件，而是先搭一个最小 Agent：

```text
LLM
+ 一段明确任务
+ 一个可读写的小目录
+ 一个可执行命令
+ 一个验证反馈
+ 一个可恢复的状态记录
```

只要这个最小链路跑通，就可以继续追问：上下文如何管理，工具如何接入，权限如何约束，反馈如何闭环，状态如何长期保存。
