# 我的技术世界观：从计算、控制到工程系统

如果把过去几年学过和写过的东西压缩成一条主线，我现在更愿意这样理解：

**计算负责表示和推演世界，控制负责让系统朝目标变化，工程负责让这一切在现实约束下真的工作。**

计算、控制、工程系统，分别对应三个层次的问题：

- 计算：世界如何被表示？
- 控制：状态如何按目标改变？
- 工程：这些抽象如何在真实条件下落地？

这三件事合在一起，大概就是我目前理解技术系统的基本方式。

## 1. 计算：把世界变成可操作的状态

计算机最基础的能力，不是“运行软件”，而是把东西表示成状态，并按照规则改变状态。

从数字电路看，状态是寄存器和触发器里的值；从 CPU 看，状态是内存、寄存器和 PC；从 C 程序看，状态是变量、堆、栈和控制流；从操作系统看，状态变成了进程、文件、设备、地址空间和调度队列。

所以计算不是从某门编程语言开始的。更底层地说：

```text
计算 = 状态表示 + 状态迁移
```

这也是为什么 `hello world` 不是一个无聊的入门程序。屏幕上出现一行字，背后其实走过了一整条链路：

```text
人的文本
-> C 源码
-> 预处理、编译、汇编、链接
-> 可执行文件
-> 操作系统加载
-> CPU 执行指令
-> syscall
-> 设备和显示系统
-> 人看到输出
```

这一行输出说明：人的意图已经成功穿过了语言、编译器、操作系统、硬件和外设，最终在现实世界里产生了可观察结果。

从这个角度看，学习计算机不是为了记住更多 API，而是为了理解人的想法如何变成机器可执行的状态迁移。

## 2. 抽象：在层级之间建立稳定接口

计算系统之所以能变得巨大，是因为它不断建立抽象层。

```text
物理电路
-> 数字逻辑
-> ISA
-> 汇编
-> 高级语言
-> 库和框架
-> 操作系统
-> 应用程序
```

每一层都在隐藏一部分细节，同时暴露一套新的接口。

ISA 把复杂电路抽象成指令。高级语言把汇编和寄存器抽象成变量、函数和控制流。操作系统把硬件资源抽象成进程、文件、socket、设备节点。网络协议把跨机器通信抽象成连接、请求和响应。

但抽象不是为了让人永远不知道底层发生了什么。好的抽象应该让人在合适的层级上思考问题，并且在出问题时有能力向下追。

比如平时写应用时，不需要天天想着 ELF、栈帧、系统调用；但当程序启动异常、动态链接失败、权限被拒绝、文件描述符泄露时，就要能顺着抽象层往下看。

所以我越来越觉得，技术能力不是“会用某一层”，而是知道：

- 当前问题处在哪一层；
- 这一层向下依赖什么；
- 向上提供什么接口；
- 抽象失效时该怎么下钻。

## 3. 控制：让状态变化服从目标

仅仅能计算还不够。

计算可以根据输入产生输出，但工程系统通常关心的是：系统能不能稳定地朝目标变化。

这就是控制问题。

在控制理论里，最经典的结构是反馈：

```text
目标 -> 控制器 -> 执行器 -> 被控对象 -> 传感器 -> 反馈 -> 控制器
```

控制的核心不是“算一个值”，而是根据当前状态和目标之间的差异，不断修正行为。

这个思想其实不只存在于自动控制课里。计算机系统里到处都是控制：

- CPU reset 后，控制权从硬件进入第一条指令。
- Firmware 把控制权交给 bootloader。
- Bootloader 把控制权交给 kernel。
- Kernel 通过中断和调度夺回或交出控制权。
- 应用通过 syscall 请求操作系统执行自己不能做的事。
- Shell 把人的命令翻译成进程、管道和文件描述符。
- Makefile 控制构建流程。
- Git 控制历史演进。
- 测试和 CI 控制代码质量。

所以“控制如何建立”可以理解得更宽：一个系统中，谁能让什么发生变化，变化是否符合目标，出错时有没有反馈和修正机制。

## 4. 工程：抽象进入现实后的代价

理论里的系统通常很干净。变量明确，模型清晰，边界稳定。

真实工程系统不是这样。

嵌入式系统里，一个控制算法能不能工作，不只取决于公式：

- 传感器有没有噪声；
- 执行器有没有饱和；
- 电源稳不稳定；
- 采样周期够不够；
- 中断会不会抢占；
- DMA 和 cache 有没有一致性问题；
- 编译优化会不会改变延时；
- 驱动和设备树有没有描述正确；
- 工具链版本会不会编不过。

所以工程不是理论的附属品。工程是在现实约束下检查抽象是否仍然有效。

我以前学 MCU、RTOS、Linux 驱动、系统镜像构建时，越来越明显地感受到：真正困难的地方往往不是单个知识点，而是系统链路太长。

一个 Linux 开发板能跑起来，至少涉及：

```text
Boot ROM
-> U-Boot
-> Kernel
-> Device Tree
-> Root Filesystem
-> Driver
-> User Space App
```

任何一环断了，最后表现出来都可能只是“板子没起来”。

这也是为什么我更喜欢先完整理解一个小系统。小系统不是玩具，而是复杂系统的压缩模型。只要它原理相通，就能帮人建立定位问题的坐标系。

## 5. 操作系统：工程系统的经典形态

操作系统在这套世界观里很重要，因为它同时体现了计算、控制和工程。

从应用视角看：

```text
操作系统 = 对象 + API
```

它把硬件资源包装成对象：进程、文件、管道、socket、内存映射、设备节点。应用程序通过系统调用操作这些对象。

从硬件视角看：

```text
操作系统 = 拥有完整控制权的程序
```

它运行在特权态，管理中断、内存、设备和调度。

从状态机视角看：

```text
操作系统 = 状态机的管理者
```

它管理许多运行中的程序状态机，并提供状态迁移接口。

这几个视角合在一起，操作系统就不再只是一本课本，而是一种理解复杂系统的原型：如何抽象资源，如何分配资源，如何隔离错误，如何提供接口，如何在多任务之间调度控制权。

## 6. 嵌入式：计算系统进入物理世界

嵌入式系统的特殊性在于，它不是只在屏幕和文件里打转，而是要真正接触物理世界。

GPIO、UART、SPI、IIC、CAN、ADC、PWM、Encoder，这些接口背后都是一件事：

```text
计算系统如何感知和作用于现实世界
```

传感器把物理量变成电信号，ADC 把连续信号变成数字量，程序根据状态计算控制量，PWM 或总线命令驱动执行器，电机或外设改变现实状态。

这里就自然接上控制。

如果说普通软件主要处理信息，那么嵌入式和机器人系统处理的是：

```text
信息 -> 决策 -> 功率 -> 动作 -> 新的信息
```

这就是计算、控制和工程系统真正汇合的地方。

## 7. AI Agent：新的意图接口

LLM 和 Agent 出现以后，这条链路又往上扩展了一层。

过去，人要让计算机做事，通常需要写代码：

```text
人的想法 -> 源代码 -> 编译器 -> 机器码 -> 操作系统 -> 硬件
```

现在，Agent 让另一条路径变得可行：

```text
人的想法 -> 自然语言任务 -> LLM -> Harness -> Tool / Code / Shell / Git -> 工程结果
```

这不是说代码消失了，而是“意图进入系统”的接口变了。

Prompt 在某些场景下像一种新的程序语言。Command / Skill 像自然语言程序包。Tool call 像系统调用。MCP 像外设和服务接入协议。Hooks 像事件触发器和权限检查。Subagent 像并发任务。仓库里的 `CLAUDE.md`、`AGENTS.md`、测试命令和文档，像 Agent 的运行环境和系统记录。

所以我现在会把 Agent 理解为：

```text
Agent = LLM + Harness
```

LLM 提供推理和语言能力，Harness 提供工具、环境、状态、权限和反馈。

如果没有 Harness，模型只是会说；有了 Harness，它才开始能做事。

## 8. Harness：AI 时代的工程系统

Harness Engineering 很像把工程系统思想搬到 AI Agent 上。

模型能力很强，但能不能稳定产出，取决于模型之外的系统：

- 任务是否清楚；
- 上下文是否足够；
- 仓库是否是事实来源；
- 工具是否可用；
- 环境是否可复现；
- 权限是否受控；
- 测试和反馈是否明确；
- 长任务状态是否能恢复。

这和传统控制系统很像。控制器本身再好，如果传感器数据乱跳、执行器不稳定、采样周期不对、电源不可靠，系统还是会失控。

AI 编程失败时，也不能只怪模型。很多时候是 Harness 断了：Agent 不知道项目规则，不知道怎么跑测试，不知道哪些文件不能改，不知道上次做到哪，不知道怎么验证自己做对了。

所以未来的软件工程师，可能不只是写代码的人，而是设计 Agent 能稳定工作的工程环境的人。

## 9. 我的整理方式

从这个角度看，后续整理笔记不应该只按“课程”来分。

课程目录当然有用，方便查找：

- C/C++
- CSAPP
- 数字电路
- 操作系统
- RTOS
- Linux 驱动
- 网络
- Claude Code

但更高一层应该按系统问题组织：

- 计算是什么：状态如何表示与迁移？
- 控制如何建立：控制权如何流动，反馈如何形成？
- 资源如何分配：对象、权限、调度、隔离如何设计？
- 系统如何连接：接口、协议、驱动、MCP 如何跨边界？
- 复杂性如何管理：分层、抽象、工具、测试、文档如何维持秩序？
- 意图如何进入系统：代码、shell、prompt、Agent 如何承接人的目标？

这些问题比具体技术更稳定。

技术会变，工具会变，模型会变，但只要我们还在构造系统，就还是要回答这些问题。

## 10. 一个暂时的结论

如果说过去几年我真正想建立的东西，不是一套“嵌入式知识库”，也不是一套“计算机课程笔记”，而是一种工程系统视角。

这套视角大概可以这样概括：

```text
用计算理解状态。
用抽象组织层级。
用控制改变系统。
用工具观察过程。
用反馈修正行为。
用工程约束检验理论。
用最小系统理解复杂系统。
```

到了 AI Agent 时代，这些东西并没有过时。相反，它们变得更重要。

因为 Agent 把人的意图接入了更高一层的自动化系统，但这个系统仍然需要状态、边界、权限、工具、反馈和工程约束。

所以从计算、控制到工程系统，再到 Agent OS，本质上还是同一个问题：

**如何把人的意图稳定、可控、可验证地作用到世界上。**
