# 隐含主线

这一篇整理一些已经在笔记里反复出现、但还没有被单独命名的想法。

## 1. 你真正关心的不是知识点，而是跨层同构

表面上你在学很多东西：

- C 语言和数据结构
- CSAPP
- 数字电路和组成原理
- 操作系统
- RTOS
- Linux 驱动
- 网络
- Claude Code

但你反复在找的不是“这门课有哪些章节”，而是不同层级之间有没有相似结构：

- 数字电路是状态机，程序也是状态机。
- 函数调用是栈帧变化，线程切换也是上下文保存与恢复。
- 文件描述符是操作系统对象的指针，MCP tool 也是外部能力的句柄。
- 编译器把 C 状态机翻译成汇编状态机，Agent 把自然语言意图翻译成工具调用和代码改动。
- Linux 驱动注册、RT-Thread 设备注册、Claude Skill/Command 注册，本质上都是把能力暴露给上一层。

这说明你的学习方式不是平铺式收集知识，而是在找“不同系统里的同一种结构”。

## 2. 你一直在反抗“定义先行”的学习方式

很多笔记里都有类似表达：教材定义很严谨，但初学者很难从定义直接建立直觉。

你更偏好的方式是：

```text
先看到一个东西为什么出现
再构造一个最小例子
然后逐步引入真实系统的复杂性
最后再回到严谨定义
```

比如操作系统：

- 不先背“操作系统是一组主管并控制计算机操作的系统软件程序”。
- 而是从一个程序为什么不能自己退出、为什么需要 `syscall` 开始。
- 再看多个程序如何共享 CPU。
- 再看为什么需要进程、虚拟内存、文件系统。

这是一种工程化的理解方式：概念不是凭空定义出来的，而是被问题逼出来的。

## 3. 最小可运行系统是你的核心方法论

你的材料里反复出现“小系统”：

- `hello world`
- `minimal.S`
- MBR 512 Byte
- 玩具操作系统
- 数字电路模拟器
- RT-Thread
- STM32 裸机
- 小型 Claude Code 项目

这些不是随手例子，而是同一个方法：

**用最小系统完整走通一条链路。**

完整比大更重要。只要链路完整，就能看到：

- 初始状态在哪里；
- 输入怎么进入；
- 状态怎么变化；
- 输出怎么产生；
- 控制权怎么转移；
- 出错时怎么观察；
- 系统边界在哪里。

然后再把这个模型映射到 Linux、真实驱动、真实 AI Agent 这类复杂系统中。

## 4. “机器永远是对的”是一种工程认识论

你在操作系统笔记里写过，调 bug 时要相信“机器永远是对的”。

这句话背后不是迷信机器，而是一个更深的判断：

```text
只要系统是确定的、可观察的、可复现的，就一定存在解释路径。
```

所以你会重视：

- gdb：观察状态。
- strace：观察 syscall 边界。
- objdump/readelf：观察二进制结构。
- qemu：复现硬件环境。
- 日志和测试：观察行为。
- 手册：找到约定。

这也是为什么 AI Agent 的验证反馈层很重要。Agent 的推理不完全确定，但它操作的工程环境必须尽量可观察、可复现、可回滚。否则人的判断会被模型输出牵着走。

## 5. 工具不是辅助，而是理解系统的感官

你写工具时不是只写“怎么用”，而是经常通过工具重新定义问题。

- `strace` 让程序变成 syscall 序列。
- `gdb` 让程序变成可单步观察的状态机。
- `objdump` 让源代码和机器码建立对应关系。
- `qemu` 让硬件启动变成可调试过程。
- `make` 让构建过程显式化。
- `git` 让变化历史显式化。
- `CLAUDE.md` 让项目知识显式化。
- Hooks 让软约束变成硬约束。

所以工具不是外围技能，而是认知工具。没有工具，就只能谈概念；有了工具，系统变得可看、可测、可改。

## 6. 控制权转移比“功能实现”更底层

很多知识点可以重新解释为控制权转移：

- Reset：硬件把控制权交给第一条指令。
- Firmware：把控制权交给 bootloader。
- Bootloader：把控制权交给 kernel。
- Kernel：把控制权交给 init 和用户进程。
- Syscall：应用把控制权交给内核。
- Interrupt：硬件强制把控制权交给内核。
- Context switch：操作系统把控制权从一个进程交给另一个进程。
- Shell：人把意图交给一个解释器，由它组织进程和文件描述符。
- Agent tool call：LLM 把自己不能完成的动作交给工具。
- Hook：Harness 在工具执行前后夺回控制权并检查策略。

这条线可以把启动、操作系统、shell、RTOS、Agent 全部串起来。

## 7. 注册机制是“能力进入系统”的通用模式

你在 RT-Thread 和 Linux 驱动里注意到注册函数：设备、驱动、总线、PIN 类，一层层向上注册。

这其实是一种非常通用的系统结构：

```text
能力本身存在
但只有被描述、注册、暴露到系统中
上层才能发现和使用它
```

对应到不同系统：

- Linux：driver/device/bus 注册到内核。
- RT-Thread：设备对象注册到内核对象系统。
- Shell：命令出现在 PATH 中。
- 动态链接：符号被导出和解析。
- Claude Code：Command/Skill 放到约定目录。
- MCP：Server 向 Client 暴露 tools/resources/prompts。
- 仓库文档：规则写进 `CLAUDE.md` 或 `AGENTS.md`，Agent 才能使用。

这解释了为什么“仓库作为唯一事实来源”很重要。没有进入系统记录的信息，对 Agent 来说就不存在。

## 8. 你对工程的理解是“抽象在约束下能否成立”

你经常把理论和工程分开看：

- 理论里，系统干净、连续、参数明确。
- 工程里，系统有噪声、延迟、饱和、功耗、温度、权限、依赖、版本和人。

所以工程不是把理论照搬过去，而是检查抽象在现实约束下是否还能工作。

嵌入式里，这些约束是：

- 芯片手册和寄存器；
- 启动地址和链接脚本；
- 中断、DMA、cache；
- 工具链版本；
- rootfs、kernel、device tree；
- 设备驱动和硬件差异。

Agent 里，这些约束是：

- 上下文窗口；
- 工具权限；
- 仓库规则；
- 环境依赖；
- 测试反馈；
- 会话压缩；
- 模型不确定性；
- 成本和时间。

换句话说，Harness Engineering 是 AI 时代的工程约束管理。

## 9. AI 不会削弱系统思维，反而要求系统思维更显式

你在早期写过：掌握计算机基础后，学习 ROS 之类的新技术会轻松，因为概念没有那么新，只是类和接口要熟悉。

Agent 也是这样。看起来全新，但底层问题仍然熟悉：

- 上下文管理对应内存管理。
- 工具调用对应系统调用。
- MCP 对应外设/服务接入协议。
- Hooks 对应中断、策略和自动化。
- Subagent 对应并发任务。
- Checkpoint/rewind 对应快照和回滚。
- 测试对应反馈控制。
- `CLAUDE.md` 对应系统配置和运行约定。

AI 能生成代码，但它不能自动替你建立系统边界、权限模型、验证闭环和长期状态记录。模型越强，越需要工程师把系统条件显式化。
