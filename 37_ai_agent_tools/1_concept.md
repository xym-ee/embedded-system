# 概念

## LLM

最底层的是 LLM(large Language Model)，大语言模型，大模型，

底层，Transformer，来源，Google 的论文，Attention is all your need。

可用级别的大模型，OpenAI，2022 年 11 月，GPT-3.5，几个月后 2023 年 3 月，GPT-4，

AI 浪潮的鼻祖，

大模型工作原理，本质上是文字接龙游戏，根据输入的内容，预测下一个最可能得输出。然后把这个输出加上前面的，再去预测下一个最可能得输出。直到结束。

所以对话看起来是一个词一个词输出答案。

## token

真实情况，大模型是一个数学函数，接受的是数字，输出的也是数字。

文字和数字中间的翻译，Tokenizer，编码和解码，文字到数字，数字到文字。

token 对应到数字上，token id，。一句话变成 token id 串，送入大模型，然后输出东西。

token 是大模型处理文本的基本单位。

每个 token 对于一个词？不一定，可以看看 openai 的模型是怎么切分的

https://platform.openai.com/tokenizer


从统计的角度讲，1 个token ≈ 0.75 个英文单词，1.5-2 个汉字

百万 tokens 大概是 70 - 80 万单词，或是 150 -200 万汉字。

更细节的，Token 如何生成，BPE 算法，。

## context


平时在网页上聊天，号线能记得之前说的话。

问题是，大模型本质上是一个数学函数，

记忆哪里来的？，很简单，把之前的整段对话历史一起打包输入大模型，计算输出就可以了。

context 的概念，上下文，大模型每次处理任务时所接收到的信息总和。

用户问题，对话历史，此外比如大模型输出的每一个 Token 也会被追加，还有工具列表，System Prompt，

可以理解为 Context 为大模型的一个临时记忆体。

下个自然的问题，这个 Context 最多能存放多少 token？这就是 Context Window 的概念。

上下文窗口：Context 能容纳的最大 token 数量，。主流的，如 GPT5.4 ，105 万。Gemini 3.1 Pro ，100 万、Claude Opus 4.6 ，100 万。

如果有一个产品手册，想让大模型通过产品手册的内容回答用户问题，该如何操作？

把文件内容和问题一起输入到大模型并不是一个很好的解决方案，手册很长，成本无法控制。

RAG 技术，从产品手册中抽取用户问题最为匹配的几个片段，然后把片段发给大模型，让大模型根据这几个关键片段来回答问题。

具体地实现原理，另一些技术。

## prompt

提示词，大模型接受的具体问题或指令。

接到输入，模型计算出结果。

prompt 怎么写，直接决定了大模型的输出质量。一个好的 prompt 应该是清晰的，具体地，明确的，。

一个专门的领域 Prompt Engineering，研究怎么把话讲清楚，让大模型更精确的理解人的意图。

有些时候不仅要告诉大模型要处理的具体任务，还要告诉他人设和做事规则，这就有两种不同的 Prompt，

User Prompt，用户输入的

System Prompt，后台配置的

System Prompt 是系统内置的，用户看不到，这些提示词会影响模型的输出。

## Tool

文字接龙游戏是根据训练数据来预测下一个词，大模型的问题，无法感知外部环境。比如问今天天气怎么样，首先今天是哪一天，地点，然后才是天气。

Tool，换个词，就是函数，给点输入就有输出。如天气查询工具，两个输入参数，城市和日期，然后不管内部怎么实现的，回来天气信息。这样就可以回答天气相关的问题了。

在 tool 的参与下，查天气的流程。

用户，大模型，天气查询工具，平台。


用户问题 -> 平台

平台 -> 大模型

平台发给大模型的除了问题，还有目前可用的工具列表，比如说是天气查询工具、计算器等。大模型分析出需求，知道要去调用工具，但是大模型唯一的能力是输出文本。要是想调用工具的话，需要借助平台的力量。大模型生成一个 调用“天气查询”的指令，大概是这么个样子

```json
{
    "tool": "天气查询",
    "参数": {
        "城市":"上海",
        "日期":"今天"
    }
}
```

发送到平台，平台真实的调用，把返回结果传递给大模型，大模型整理成一句好看的 AI 话。

比如：今天天气还不错。转发给平台，平台再给用户。


大模型：选择需要调用的工具，生成需要的参数。归纳总结，拿到执行结果后总结。

工具：具体的外界交互的动作。

平台，串联整个流程。

tool 就是给大模型提供一套可以调用的外部能力。

## MCP

上面的流程还有些工程问题，
- 凭条要把工具列表传给模型
- 还要能调用工具

首先要把工具接入平台，问题来了，接入规范，每个平台都不一样。

如果是 OpenAI，需要按照他的规范来，

用的 Claude，需要按照 Anthropic 的规范写一套代码

用的 Gemini，需要按照 Google 的规范写一套代码

同一个工具每个平台的接入工具都不一样。搞一个统一的接入规范，

MCP (Model Context protocol)，模型上下文协议。统一的工具接入标准。

工具通过 MCP 接入。

## Agent

有了 tool 和 MCP，大模型已经有和外部世界交互的潜力了。

还差点东西。

尝试让大模型做点更复杂的事情，如问题：

今天天气怎么样，如果下雨的话，查一下附近的卖雨伞的店。

有这些工具可用：定位工具，天气工具，商店工具

要解决这个问题，需要调用多次工具，从大模型的视角来看。，流程

大模型思考，用户问天气，那么需要知道位置，有定位工具，可以先用一下。发调用定位工具指令，获取结果

大模型思考，查询这个位置的天气，有个天气工具可以用，调用天气工具指令，回来结果，有雨

大模型思考，有雨，然后根据指令调用店铺查询，发现有个便利店。

大模型思考，任务全部达成，可以给最终答案了。

在这个过程中，大模型一步一步思考当前情况，决定下一步做什么。已经初具自主规划能力了。

这种能够自主规划，自主调用工具，直到完成任务的系统为 Agent，。比如 Claude Code，Codex，Gemini CLI，他们的 Agent 构建模式，比较经典的，ReAct，Plan And Execute，


## Agent Skill

到了 Agent，已经很强大了，自主规划调用工具，持续工作完成任务。大多数人也都是这么用的。

但在实际的高频使用中，还会有一些小问题。

如果为个人助手的 agent 希望他每次出门前帮忙查天气，提醒带东西。个人出门习惯。如下雨带伞，光照强戴帽子，空气差戴口罩，手机身份证必带。然后还希望个人助手不要太啰嗦，回答最精简的问题。按照特定格式输出如：

```
[结论一句话]
一句话总结

[出门清单]
- 物品(原因)
- 物品(原因)
```

如果在没有预设的情况下，直接问：我要出门，带些什么？

大概率一堆废话，不知道个人习惯，输出格式。
