# 个人工作空间的软件架构设计

过去整理知识时，我更关心的是“这篇笔记应该放在哪个目录”。随着内容逐渐增多，又开始使用 Codex、Claude Code 一类 Agent，问题发生了变化：现在需要考虑的不只是如何保存笔记，还包括 Agent 从哪里开始工作、怎样找到相关资料、哪些内容可以读取、结论应该写回哪里，以及私人内容怎样与公开内容隔离。

因此，我真正想设计的可能不是一个普通知识库，也不是一个只能由 Obsidian 打开的笔记目录，而是一套**人和 Agent 共用的持久化工作空间**。

这套系统以 Markdown 和 Git 保存长期状态，以 `AGENTS.md` 描述协作规则，以多个独立仓库划分知识和工程边界，再由一个私有总入口完成跨仓库的发现、路由和权限控制。Obsidian、GitBook、博客和 AI 检索都只是建立在这些文件之上的不同视图。

## 1. 问题是怎样产生的

当前积累的内容并不只是一类数据，大致包括：

- 计算机、嵌入式、电子、控制等长期学习笔记。
- 具体芯片、板卡和工程项目的源码与调试记录。
- 当前任务、项目状态、个人想法和历史决策。
- 可以通过 GitBook 或博客公开发布的内容。
- 只能保存在私人环境中的工作资料和生活记录。

这些内容已经分散在多个 Git 仓库和磁盘目录中。有的仓库可以公开，有的必须私有；有的按照 GitBook 的结构组织，有的是完整源码工程，还有的只是个人工作上下文。

如果只是给人使用，这种分散通常不是大问题，人可以依靠记忆找到文件。但 Agent 每次进入一个新会话时没有稳定的长期记忆，它首先需要重新回答几个问题：

1. 这里是什么工作空间？
2. 当前任务属于哪个领域？
3. 哪份文件是可信的权威来源？
4. 哪些目录允许读取、修改或对外发布？
5. 完成任务后，状态、决策和知识分别写回哪里？

聊天记录可以提供临时上下文，但不能作为可靠的长期存储。真正能够跨会话、跨模型、跨工具保存下来的，仍然是文件和版本历史。

## 2. 设计目标

这套个人工作空间希望满足下面几个目标。

### 2.1 人和 Agent 都能理解

文件首先应该能够被人直接阅读，同时也要给 Agent 提供明确入口、边界和写回规则。不能为了机器检索，把知识变成人难以维护的数据结构。

### 2.2 子仓库保持自治

`embedded-system`、`electronics` 等仓库拥有自己的 `README.md`、`AGENTS.md`、导航、Git 历史和发布流程。即使脱离私人总入口，单独克隆和打开后仍然可以正常阅读，也可以直接交给 Agent 工作。

### 2.3 总入口负责组合，而不是吞并

私有总入口知道有哪些知识库和工程仓库，知道它们在当前电脑上的位置以及各自的权限，但不复制所有内容，也不取代子仓库内部规则。

### 2.4 核心数据不绑定具体工具

长期内容保存在标准 Markdown 和普通文件中，历史由 Git 管理。Obsidian、GitBook、博客、全文搜索和向量检索可以替换或重新生成，但不应成为知识存在的前提。

### 2.5 公开、私人和敏感内容有清晰边界

系统必须区分“可以读取”“可以修改”“可以送入外部模型”“可以公开发布”等不同权限，不能简单地用一个 `public/private` 标签代替全部安全规则。

### 2.6 允许渐进演化

不一次性迁移所有旧笔记，也不提前设计完整的元数据系统。先建立最小接口，再让真实使用中的问题推动结构继续演化。

## 3. 总体架构

整个系统可以分成控制面、内容域和表现层。

```text
                         人 / AI Agent
                              |
                    private workspace root
                 AGENTS.md + workspace manifest
                              |
          +-------------------+-------------------+
          |                   |                   |
     知识仓库              工作状态仓库          工程源码仓库
 embedded-system          life-context          product-code
 electronics             projects              board-firmware
 control-theory           decisions             experiments
          |                   |                   |
          +-------------------+-------------------+
                              |
                Obsidian / GitBook / Blog / Search
```

这里的总入口更像一个 **control plane**：它负责发现、组合和协调。具体知识、项目状态和源码仍然保存在各自仓库中，它们构成实际的 **data plane**。

总入口不是包含一切的超级仓库，而是一组自治工作区的私有联合入口。

## 4. 两种 Agent 启动方式

子仓库已经拥有自己的 `AGENTS.md`，因此系统天然支持两种启动方式。

### 4.1 单仓库启动

当任务只涉及嵌入式笔记时，可以直接打开对应仓库：

```text
Agent
  -> embedded-system/AGENTS.md
  -> README.md / SUMMARY.md
  -> 相关专题和项目文件
```

这种模式不依赖私人总入口。公开仓库不会因为缺少私人配置而失去可用性，也不会知道其他私人仓库或公司工程的存在。

### 4.2 联合工作区启动

跨领域工作从私有总入口开始：

```text
Agent
  -> root/AGENTS.md
  -> workspace.yaml
  -> 判断任务所属领域和权限
  -> 目标仓库/AGENTS.md
  -> 项目 CONTEXT / STATUS / DECISIONS
  -> 实际笔记或源码
```

根 `AGENTS.md` 可以直观地类比为 boot 程序或 0 号进程。若按照 Linux 用户空间的职责进一步类比，它又很像 `init` 或 PID 1：建立最初的运行环境、加载全局规则、发现资源，然后把具体工作交给对应的局部系统。

这两个入口之间应该遵循一条单向依赖原则：

> 根工作区知道子仓库，子仓库不必知道根工作区。

## 5. 根规则与局部规则

两级 `AGENTS.md` 不应该重复保存相同内容，而应该各自承担不同职责。

| 根 `AGENTS.md` | 子仓库 `AGENTS.md` |
| --- | --- |
| 定义整个工作区是什么 | 定义本仓库是什么 |
| 规定全局启动和路由流程 | 规定仓库内的读取顺序 |
| 规定跨仓库安全边界 | 规定内容分类和修改方式 |
| 说明状态应写回哪个权威仓库 | 说明具体文件应放在哪里 |
| 定义局部规则的加载机制 | 说明构建、检查和发布方法 |
| 处理多个仓库之间的协调 | 处理本领域内部任务 |

根规则是全局默认和安全下限，局部规则可以更具体，但不能突破根规则规定的权限边界。

根 `AGENTS.md` 应该保持短小和稳定。个人背景、当前任务、仓库详细清单以及经常变化的状态不应全部塞进启动文件，否则每次启动都会读取大量无关内容。

## 6. 私有总入口的最小结构

一个最小的总入口仓库可以是：

```text
personal-workspace/
├─ AGENTS.md                  # Agent 启动协议和全局不变量
├─ README.md                  # 给人看的工作区总入口
├─ CONTEXT.md                 # 当前阶段的低频全局背景
├─ workspace.yaml             # 逻辑仓库注册表
├─ mounts.local.example.yaml  # 本机路径配置示例
├─ decisions/                 # 跨仓库架构决策
├─ schemas/                   # 状态、权限和文档约定
├─ tools/                     # 检查、索引和恢复工具
└─ docs/
   └─ architecture.md         # 完整架构说明
```

其中 `workspace.yaml` 保存可共享的逻辑信息：

```yaml
repositories:
  embedded-system:
    role: knowledge
    visibility: public
    entry: README.md
    agent_rules: AGENTS.md

  company-firmware:
    role: source-code
    visibility: confidential
    default_access: read-only
    agent_rules: AGENTS.md
```

不同电脑上的实际路径放进不提交 Git 的本机配置：

```yaml
repositories:
  embedded-system:
    path: D:\workspace\embedded-system

  company-firmware:
    path: E:\work\company-firmware
```

Agent 始终引用稳定的逻辑名称 `embedded-system`，本机配置负责把它解析成实际路径。这样可以保持工作空间的逻辑结构一致，而不要求每台电脑具有完全相同的盘符和目录。

## 7. 为什么先用注册表，而不是 Git submodule

这个工作空间包含公开仓库、私人仓库、其他磁盘上的源码工程，以及各自独立的发布和版本节奏。总入口通常只需要知道“有哪些仓库以及如何找到它们”，并不总是需要把所有仓库锁定在同一个提交上。

因此早期更适合使用：

```text
manifest / registry + independent repositories
```

而不是立即把全部内容改成 Git submodule。

如果以后确实需要完整复现某个时间点的工作环境，可以从注册表生成一个 lock 文件，记录各仓库 URL、分支和 commit。注册表表达期望的逻辑组成，lock 文件表达一次确定的工作区快照。

根仓库还应显式忽略内部独立 Git 仓库，避免一次无意的 `git add .` 把它们作为嵌套仓库记录进去。

## 8. 持久化的不只是知识

Agent 想持续理解一个人，仅有领域笔记还不够。至少需要区分下面几类持久化信息：

| 信息 | 回答的问题 | 推荐载体 |
| --- | --- | --- |
| 工作规则 | 应该怎样行动 | `AGENTS.md` |
| 长期背景 | 为什么建立这个系统 | `CONTEXT.md`、架构文章 |
| 当前状态 | 现在进行到哪里 | `STATUS.md`、`TASKS.md` |
| 历史决策 | 为什么选择当前方案 | `DECISIONS.md`、ADR |
| 长期知识 | 已经形成了什么理解 | 领域笔记 |
| 原始证据 | 结论来自哪里 | 资料、实验日志、链接 |
| 权限边界 | 什么能读、写和发布 | 根规则、注册表、局部规则 |

其中最重要的不是文件名本身，而是**单一权威来源**。同一个项目的当前状态不能同时由两个工作系统维护，否则 Agent 不知道应该相信哪一份，也不知道任务结束后写回哪里。

对话可以帮助当前 Agent 工作，文件才负责让下一次会话继续工作。

## 9. 权限与信任域

根仓库必须是私有的，因为它会暴露整个个人工作空间的地图，甚至可能记录私人和公司仓库的存在。但“私有仓库”不等于可以在里面保存密码、密钥或所有敏感原文。秘密仍应交给专门的凭据系统管理。

对一个知识域，至少可以分别考虑四种能力：

- `read`：Agent 是否可以读取。
- `write`：Agent 是否可以修改。
- `index`：内容是否可以进入全文或向量索引。
- `publish`：内容是否可以进入 GitBook、博客或其他公开输出。

例如，一个公司源码仓库可能允许本地 Agent 在明确任务中只读分析，但禁止进入外部索引，也禁止在公开笔记中复制实现细节。

Agent 启动时也不应递归扫描所有仓库。总入口只需要知道资源存在，等任务真正涉及某个领域时再读取它的局部规则和内容。这既节省上下文，也减少不同信任域之间的信息污染。

## 10. Markdown 和 Git 是核心，其他工具是视图

这套设计不需要把长期知识“迁移成 Obsidian 格式”。更合适的方式是让 Obsidian 直接管理现有 Markdown 文件。

```text
Markdown + Git
├─ Obsidian：人的浏览、链接和编辑界面
├─ GitBook：技术知识的公开阅读界面
├─ Codex / Claude Code：理解、执行和整理
├─ 全文搜索 / RAG：按需建立的检索层
└─ Blog：选择性整理后的公开输出
```

对于需要发布到 GitBook 的仓库，正文仍优先使用标准 Markdown 和相对链接，避免让 Obsidian 专属语法成为阅读前提。搜索索引、知识图谱和 embeddings 都应该是可重新生成的构建产物，不是新的唯一事实源。

这种设计把内容模型与表现工具分开。以后即使更换 Obsidian、GitBook 或 Agent，底层知识仍然可读、可版本化，也可以继续演化。

## 11. Agent 的一次完整运行

从私有总入口启动时，一次任务可以按下面的过程运行：

```text
1. 读取根 AGENTS.md，建立全局规则和安全边界
2. 读取 workspace.yaml，发现可用的逻辑知识域
3. 根据用户目标选择最小相关领域
4. 解析当前电脑上的实际挂载路径
5. 读取目标仓库的 AGENTS.md 和入口文件
6. 按需读取项目 CONTEXT、STATUS、DECISIONS 和具体材料
7. 执行任务，并通过测试、链接检查或人工审查验证结果
8. 把状态、决策、知识和交付物写回各自的权威位置
9. 汇报改动和仍然存在的不确定性
```

这个过程体现了渐进式披露：启动阶段只读取最少的稳定规则，进入具体任务以后再逐层加载相关上下文，而不是把整个个人文件系统一次性塞进模型上下文。

## 12. 背后的软件工程思想

这套文件系统设计实际上综合使用了多种软件工程思想。

| 工作空间设计 | 对应思想 |
| --- | --- |
| 不同主题使用独立 Git 仓库 | 模块化、边界上下文、polyrepo |
| 子仓库拥有自己的 `AGENTS.md` | 自描述组件、局部契约 |
| 子仓库可以独立打开 | 自治、低耦合 |
| 私有总入口负责发现和组合 | Composition Root、控制面 |
| 根知道子仓库，子仓库不依赖根 | 单向依赖、封装 |
| `workspace.yaml` | manifest、服务注册 |
| 本机路径单独配置 | 配置与内容分离、环境适配 |
| Markdown 与 Git 保存事实 | Docs as Code、可追溯性 |
| Obsidian、GitBook、搜索作为视图 | 核心模型与表现层分离 |
| 公开、私人和公司仓库分区 | 信任域、最小权限 |
| `STATUS`、`DECISIONS` 与知识分开 | 关注点分离、状态建模 |

它同时也带有操作系统和分布式系统的味道：启动、挂载、权限、注册发现、局部自治和跨域协调。但这些类比是用来帮助设计的，不需要机械地把个人文件系统实现成真正的操作系统或微服务平台。

## 13. Git 不是完整备份

Git 很适合保存文本、历史和决策，但不能自动解决全部备份问题。下面这些内容可能不在 Git 历史中：

- 尚未提交的修改。
- 被 `.gitignore` 排除的私人文件。
- 大型附件、照片、录音和数据集。
- 本机路径配置和开发环境。
- 密钥、账号与其他凭据。

因此还需要区分两个目标：

- **可重建**：通过注册表、仓库地址和环境说明恢复工作区结构。
- **已备份**：原始文件和未提交内容确实存在独立副本。

以后可以增加一个只读健康检查，报告仓库是否存在、当前分支、未提交修改、是否落后远端、最近备份时间以及索引是否过期。

## 14. 渐进实施路线

这套架构不需要一次完成，可以从最小版本开始。

### 第一阶段：建立私有总入口

- 创建根 `README.md` 和 `AGENTS.md`。
- 建立最小 `workspace.yaml`。
- 只注册现有几个核心仓库，不移动任何内容。

### 第二阶段：明确权威状态

- 确定哪个仓库维护当前项目和任务。
- 把另一个重叠系统标为实验、迁移目标或历史版本。
- 规定状态、决策和长期知识分别写回哪里。

### 第三阶段：选择两个仓库试运行

- 一个公开知识库，例如 `embedded-system`。
- 一个私人工作状态仓库。
- 验证单仓库启动和联合启动都能正常工作。

### 第四阶段：增加自动检查

- 检查仓库是否挂载。
- 检查失效链接和导航漂移。
- 检查未提交修改和分支状态。
- 检查敏感目录是否错误进入索引或发布流程。

### 第五阶段：增加检索和发布视图

- 先建立确定性的全文索引。
- 再根据真实需求增加语义检索或 embeddings。
- 让 GitBook、博客和其他输出保留到原始知识的引用关系。

## 15. 需要避免的失败模式

### 根 `AGENTS.md` 变得过大

启动文件只应保存稳定规则和加载方法。大量知识、个人经历和动态任务应放在其他文件中按需读取。

### 多个系统同时维护同一状态

双写会产生冲突。允许有多个视图，但同一事实只能有一个权威写入位置。

### 过早设计大量元数据

如果每写一篇笔记都要填写十几个字段，系统很快会因为维护成本而失效。元数据应该为真实检索、权限和发布需求服务。

### 先做向量数据库，再整理内容边界

检索能力不会自动提高知识质量。没有区分事实、草稿、日志和过期状态时，向量检索只会更快地找出含义不清的内容。

### 把所有内容自动暴露给 Agent

资源可发现不等于可以读取。跨私人、公开和公司信任域时，应默认最小权限并按任务加载。

### 工具反过来控制知识结构

Obsidian、GitBook 和某个 Agent 都可能更换。核心文件格式和仓库边界不应只服务于其中一个工具。

## 16. 怎样判断这套系统是否有效

可以用一个全新会话做最简单的验收。Agent 只读取入口文件以后，应当能够正确回答：

1. 这个工作空间里有哪些领域？
2. 当前任务应该进入哪个仓库？
3. 哪份文件是当前状态或知识的权威来源？
4. 哪些内容不能读取、索引或公开？
5. 任务完成以后，结果应该写回哪里？

如果 Agent 能回答这些问题，并且既能从总入口跨仓库工作，也能在单个子仓库中独立工作，那么这套启动、路由和持久化机制就已经成立。

## 总结

个人工作空间不只是一个文件夹，也不只是一个知识库软件。它可以被理解成一套长期运行的人机协作系统：

- Git 仓库是自治的知识域和工程域。
- Markdown 和普通文件是可迁移的持久化格式。
- `AGENTS.md` 是人和 Agent 之间的协作协议。
- 私有总入口是跨仓库的控制面和组合根。
- `STATUS`、`DECISIONS` 和领域笔记保存不同性质的记忆。
- Obsidian、GitBook、博客和 AI 检索是建立在事实源之上的视图。

最终目标不是让 Agent 读取所有文件，而是让它每次都能找到完成当前任务所需的最小上下文，理解边界，执行工作，并把新产生的状态和知识写回正确的位置。

> 根入口定义 Agent 如何醒来，注册表告诉它这个世界里有什么，子仓库保存各自的事实，状态文件让工作能够跨越一次次对话继续进行。
