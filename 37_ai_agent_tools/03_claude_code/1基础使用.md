

# 基础使用



## 基础使用

- CLAUDE.md 实操 
- 启动参数和交互模式
- 上下文管理
- 模型切换，输入效率


`CLAUDE.md` 把项目规则、常用命令、安全边界、验收标准写进 Claude Code 的长期项目上下文。

关注：
- 怎么让 Claude 先只读分析项目
- CLAUDE.md 里该写什么
- 常用命令必须来自项目文件，不要让 AI 瞎编
- 怎么验证 CLAUDE.md 是否生效

从“会用 Claude Code”到“让 Claude Code 稳定服务一个项目”的分水岭。


启动方式和会话恢复

```sh
claude
claude --project /path/to/project

# 继续最近会话
claude -c
claude -r <session-id>
claude --verbose

# 并行处理多个任务
claude --worktree
```

`--dangerously-skip-permissions` 谨慎使用



下文管理，这是高频使用点：
```sh
/context
/compact
/clear
```




rewind/checkpoint 双击 esc，  /rewind

重点理解三种回退：
- 仅恢复代码
- 仅恢复对话
- 代码和对话都恢复


输入效率：
- @文件路径
- !命令
- /memory
- 多行输入
- Ctrl+R 搜索历史

其中 `@文件路径` 很重要，可以减少 Claude 乱搜上下文；`!命令` 适合你自己直接跑检查命令。


更多的，git + claude 配合

```sh
# 1. 早上恢复昨天的会话
claude -c

# 2. 检查状态
/status

# 3. 开始工作
我今天要完成用户认证模块

# 4. 工作过程中定期检查Token使用
/context

# 5. Token使用超过60%时压缩
/compact

# 6. 完成重要功能后导出对话
/export ~/docs/auth-implementation.md

# 7. 下班前重命名会话
/rename auth-module-day2
```


checkpoint 大胆重构。

导出对话，给团队看
```sh
# 导出纯文本对话
/export shared/auth-discussion.txt
```

## 命令

`/命令` 触发预设操作

自定义命令就是 .claude/commands 下的 md 文件。

skill 也是。

临时/轻量/项目内快捷入口 -> Commands

复杂/长期/可复用/跨项目能力 -> Skills

比如有个 /write 命令，找 write.md 文件，读内容作为提示词，传入参数到 `$ARGUMENTS`，然后运行


几类命令，程序内置，全局命令，skills


自定义命令本质是 Markdown 文件：

.claude/commands/code-review.md -> /code-review


一个命令通常包含：

```md
---
description: 命令说明
argument-hint: <参数提示>
allowed-tools:
  - Read
  - Grep
---

# 命令正文

任务说明、执行步骤、输出格式。
参数：$ARGUMENTS
```

一个 hello world 的例子。

```md
---
description: 热情问好
argument-hint: <问候对象>
---

用户想要问好的对象是 $ARGUMENTS

如果没有名字，那么就称呼为朋友。

热情问好即可。
```

claude 启动后运行 /hello world。



关于命令的作用域和命名空间

两个位置
```sh
.claude/commands/      # 项目级，适合团队共享
~/.claude/commands/    # 用户级，适合个人通用命令
```

子目录会变成命名空间

```sh
.claude/commands/dev/code-review.md # /dev:code-review
.claude/commands/test/generate.md   # /test:generate
```



Command / Skill ~= 面向 AI Agent 的“自然语言程序”

它和 Unix 应用确实有不少相似点：

| Unix 应用 | Claude Code Command / Skill |
|---|---|
| 可执行文件 / shell script | .md 命令文件 / skill 包 |
| 命令名 | slash 命令名 |
| argv 参数 | $ARGUMENTS |
| stdin / 文件输入 | @file、Read、Grep、上下文 |
| stdout 输出 | Claude 的回复 / 结构化报告 |
| exit code | 成功/失败说明、验收标准 |
| pipe 组合 | 命令链式调用、工作流编排 |
| 权限模型 | allowed-tools、沙箱、确认机制 |
| man page | description、argument-hint、README / SKILL.md |
| PATH | 项目级 / 用户级 commands 或 skills 搜索路径 |
| cron / systemd | 后面 Channels、计划任务、Automations 一类能力 |

但有一个关键差异：

Unix 程序执行的是确定性代码；Command / Skill 执行的是“受约束的推理流程”。

所以它不是传统意义上的程序，而更像：

prompt + 参数 + 工具权限 + 执行流程 + 输出契约

你这个“自然语言开发一个应用程序”的说法很准确。进一步可以拆成：

应用名：/dev:code-review
输入：$ARGUMENTS = 文件路径
能力：Read + Grep
流程：读取文件 -> 分析问题 -> 输出报告
权限：不能写文件、不能执行 Bash
输出：结构化 code review

一个好的 Command / Skill 应该像一个好 Unix 工具：

1. 单一职责：只做一件事，比如 review、生成测试、写 changelog。
2. 输入明确：参数格式清楚，缺参数要报错。
3. 输出稳定：固定报告格式，方便人读或后续命令继续处理。
4. 权限最小化：只开放必要工具。
5. 可组合：多个小命令组合成工作流，而不是一个巨大的万能命令。
6. 可移植：项目级放项目规则，用户级放个人通用工具。
7. 可维护：命令文件本身进入版本控制，团队一起演进。

学 Skills 时，这个类比会更明显：Command 更像小脚本或 CLI wrapper，Skill 更像一个带说明书、资源文件、脚本和约束的“小应用包”。




个比较成熟的 skill 包结构可能会长这样
```sh
repo-review-skill/
  SKILL.md                    # 核心行为，尽量 agent-neutral
  skill.yaml                  # 元信息、权限、能力需求
  references/
    review-checklist.md
    security-rules.md
  examples/
    input-diff.patch
    output-report.md
  scripts/
    collect-diff.sh
    run-tests.sh
  adapters/
    claude-code.md
    codex.md
    opencode.md
    openclaw.md
  tests/
    fixtures/
    golden/
```

skill 不是简单 prompt。

skill 是一种以自然语言为主要源码格式、以 agent 为 runtime、以工具能力为系统调用接口的软件包。只是这次的“编译器/解释器”不是 gcc、node、python，而是 LLM agent。
